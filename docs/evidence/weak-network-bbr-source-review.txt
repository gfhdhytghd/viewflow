Source assessment, 2026-10-29
Local Cargo registry: quinn-proto 0.11.19 (Cargo.lock), quinn 0.11.11.

congestion/bbr/mod.rs explicitly says "Experimental! Use at your own risk."
This is the bundled implementation, not a claim about Linux BBRv2/v3.
BbrConfig only exposes initial_window; default is 200*1200 = 240000 bytes.
CubicConfig only exposes initial_window; default is 12000 bytes. There is no
public loss tolerance/beta setting in this version. Enlarging Cubic's initial
window does not remove steady-state multiplicative loss response.

BBR models maximum delivery bandwidth and minimum RTT, with Startup, Drain,
ProbeBw and ProbeRtt states. Loss enters conservation/growth recovery and
subtracts lost bytes from a recovery window; it is not immune to loss.
ProbeBw gains alternate 1.25/0.75/1; target cwnd is approximately 2*BDP.
ProbeRtt uses 0.75*BDP here, not the common four-packet description.
Important implementation limits from source:
- bw_estimation.rs samples adjacent send/ACK events, not a per-packet delivery
  snapshot. It updates the max filter only for a strictly larger non-app-limited
  sample. A previously large estimate therefore cannot age downward through
  lower samples. Warmup on clean loopback before enabling netem matters.
- BBR's calculated pacing_rate is only returned in ControllerMetrics for qlog.
  connection/mod.rs:627 calls Pacer::delay with smoothed RTT and cwnd instead.
  connection/pacing.rs refills at 1.25*cwnd/RTT, with 10..256 MTU burst capacity.
  Selecting BBR does not install its gain-controlled pacing rate.
- min RTT uses RttEstimator::min(); probing does not create an independently
  windowed RTT estimator. Do not infer a production-grade model from the name.

QUIC DATAGRAM payloads are not automatically retransmitted. Their packets
remain ACK-eliciting and congestion controlled/paced, so BBR receives send,
ACK and loss events for media as for reliable streams. W1 NACK remains separate.
The controller factory is local TransportConfig state, not a TLS/QUIC transport
parameter or an application capability. Mixed Cubic/BBR senders need no wire
negotiation; tests/congestion.rs checks both stream and DATAGRAM directions.

Implementation decisions:
- One shared builder, selected once per connection, explicit Cubic and BBR API.
- VIEWFLOW_CONGESTION_CONTROL override is process-local, cubic|bbr.
- Existing 16MiB TLS-server, 64KiB coded-client, audio and default buffers remain
  unchanged. Keepalive call sites and idle timeout remain unchanged.
- No per-frame config reads, allocations or locks. No input/focus/capture work.
- Harness adds wifi1 HighQuality, controller/mode selection, process coordination
  and private-netns qdisc sampling every 0.5s. Random netem seeds remain recorded
  in raw tc output; these are repetitions, not matched-seed confidence intervals.

Alternative evaluation:
Cubic's public configuration has no loss-response tuning. A larger initial
window cannot fix the steady-state limit. Bundled BBR fails wifi1 Auto and
cap20 latency. Rather than fork Quinn's BBR estimator and pacer, evaluate a
small local DelayCubic wrapper around Quinn's own Cubic window arithmetic.
It gates isolated loss on smoothed RTT inflation (>1.5*baseline AND +15ms),
also reduces on queue growth without loss, and preserves ECN and persistent
congestion events. Quinn loss detection/retransmission, pacing and connection
timeouts remain untouched. No new session exit or per-frame allocation/lock.
First variant used two five-second baseline buckets and improved wifi1 but
underutilized cap20 during the warm-clean -> shaped-path transition. Retain
weak-network-bbr-delay-cubic.txt; evaluate two one-second buckets separately.
The shorter window is a route-change response choice, not a security timeout.

Coordination correction: counting a sleeping Python harness as an active
measurement caused mutual waiting with the sibling pipeline harness. /proc
showed both wrappers sleeping and no netem child. Stopped only this worktree's
waiting wrapper, then changed the guard to record the full pgrep inventory but
wait for actual --exact --ignored netem test processes. A waiting wrapper is
not measuring. No sibling process/file was changed.

Final candidate: two one-second baseline buckets (minimum spans ~1..2 seconds).
On a confirmed upward baseline shift >15ms, if cwnd is below the original
initial window, restart Quinn Cubic at that original 12000-byte initial window.
This bounds the renewed probe instead of retaining a two-packet congestion
avoidance crawl after a propagation-delay change. Cache/reuse Arc<CubicConfig>;
no allocation or lock in ACK processing. MTU updates are retained across rebase.
A dedicated test checks renewed congestion still reduces the restored window.
The first test failed because the rebase hook was missing (8400 vs 12000);
weak-network-bbr-rebase-test-failed.txt preserves it. The assertion was retained
and the hook added; transport checks pass afterward.

No claims of Internet fairness or deployment certification: delay-only loss
gating cannot prove whether a small-buffer drop without RTT inflation is random
or congestive. Application RateController remains active; ECN and persistent
congestion retain Quinn's normal response. Competing flows, shallow buffers,
real Wi-Fi, cross-host timing, native decoding/presentation and visual quality
require separate tests. The measured scope is the owned single-lane harness.

Decision: default DelayCubic, with explicit Cubic and BBR overrides. Final nine
scenarios plus seven same-binary repeats support wifi1 Auto improvement and
bounded Auto cap20/cap8 latency. cap20 HighQuality p95 ranges overlap but the
first final run is 2.7ms above the first Cubic run; no strict zero-regression
claim. Keep all variants, failed test and 54 successful netem rows. Final
checks: workspace 985/0/4 ignored; NVENC 749/0/16 ignored; required clippy exit 0.
Real Wi-Fi/native presentation/fairness remain unverified. No push/deployment.
