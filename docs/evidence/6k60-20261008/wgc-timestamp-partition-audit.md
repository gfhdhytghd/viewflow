# WGC timestamp and completion audit

2026-10-09. Added identity-deduplicated `analyze-wgc-timestamp-partitions.py`, evaluated progressive32/33/34. This is offline analysis of existing actual6K runs; no input/focus injection or new desktop mutation.

SystemRelativeTime→callback-entry differences include negative values. Medians32:-4.401ms,33:+1.532ms,34:-0.767ms; minima-7.566,-11.278,-8.836ms. Source implementation reads frame.SystemRelativeTime().count() directly and callback clock uses integer QPC/frequency conversion to100ns. Therefore do not interpret this metadata subtraction as a causal GPU-completion→delivery interval. The property documentation describes compositor render time, not a CPU-observed completion fence; current behavior needs independent corroboration. Official reference: https://learn.microsoft.com/en-us/uwp/api/windows.graphics.capture.direct3d11captureframe.systemrelativetime . Microsoft sample issue127 discusses timestamp/update limitations, but does not establish the cause of our future-valued timestamps: https://github.com/microsoft/Windows.UI.Composition-Win32-Samples/issues/127 .

Independent fixture fence correlation from progressive34:1452 matched6K records, generation→CPU-observed fence completion median11.892ms/P9515.675; observed completion→WGC entry median17.462/P9522.498/min7.527ms. The CPU observation is an upper bound on actual GPU completion, so the subsequent gap is a lower bound on actual completion-to-callback gap. It cannot distinguish compositor scheduling, driver work, capture copies, or event dispatch. Entry→consumer median0.0094ms/P950.0151 confirms application callback bookkeeping is small. Do not subtract independent percentile summaries to manufacture a pipeline breakdown.

Next optimization experiment should target compositor/capture GPU scheduling or capture implementation rather than CPU callback bookkeeping. Preserve generation→actual CPU callback and same-frame Wayland feedback as the measurement basis. No performance target achieved by this audit.
