# Actual Dolphin DMA-BUF capture and encoding — 2026-09-05

This is local capture-to-encode evidence, **not Windows presentation or the
two-frame end-to-end acceptance**. No Windows service, firewall, task, or
deployment marker was changed in this slice.

## Implemented path

HyprCapture `window-gpu` render loop -> HCGF/SCM_RIGHTS image + native fence ->
authenticated Rust GPU receiver -> thread-bound C ABI -> EGL import -> CUDA
repair/unpremultiply/shadow -> BT.709 limited NV12/NVENC H.264 High + separate
raw alpha -> explicit HCGR release. Native failure never sends HCGR; the local
session is stopped. Stop applies only to its own stream ID.

`native-gpu-nvenc` is an opt-in Cargo feature; existing CPU capture and encoding
remain separate. The GPU control record uses top-level `window-gpu` transport
but nested defaults `mode: window`, matching the plugin's capture semantics.

## Follow-up source changes (not included in r5)

Live metadata and datagram admission now share one absolute dispatch deadline
derived from the original mapped source capture time. Once it expires, remaining
fragments are not queued, a partial dispatch is not counted as a complete send,
and only the exact receiver REJECT permits a later IDR recovery. A partial
metadata write terminates the session. Already queued QUIC datagrams are not
magically recalled by this change. Decode-only warmup remains separate.

Tests exercise the actual dispatch helper with blocked, already-expired and
immediately-ready futures, in addition to original-time budget arithmetic.
This is stale-work containment, not proof that any frame meets its deadline.

The GPU encoder now uses GOP 120 with real forced-IDR recovery rather than
making every frame an IDR. QP 10, dimensions, alpha fidelity and BT.709 are
unchanged. Native integration feeds an IDR/P/P/forced-IDR sequence through one
software decoder and verifies changed colors as well as NAL type, picture type
and alpha. Synthetic AU sizes were 1006/117/4184/1006 bytes: unchanged P saves
bytes, but a changed P is not guaranteed smaller than an IDR. Native CTest 5/5
and Rust example tests 22/22 pass. Candidate release SHA-256 after these changes:
`0e95c5205c4c9a344fd89cc3710bdaa8dd354e1d9f391d147f315e0f54b13889`.
It has not yet been used for a cross-host trial.

A scheduling diagnostic on Windows requested twenty 1 ms Thread.Sleep waits:
observed min/mean/max 7.636/18.260/22.926 ms. Concurrent link sanity checking
was not performed, but a nearby five-packet Linux ping observed mean 0.470 ms,
zero loss. This raises a timer-resolution hypothesis, not proof of Quinn's
actual timer behavior. Microsoft's
[timeBeginPeriod contract](https://learn.microsoft.com/en-us/windows/win32/api/timeapi/nf-timeapi-timebeginperiod)
requires matching timeEndPeriod and describes per-process behavior from
Windows 10 version 2004, with Windows 11 occlusion caveats. Any probe must
release its own request and must not change persistent host timer policy.

The independent A/B/A probe (`/tmp/viewflow-win-timer-diagnostic.ps1`) verified
Windows build 10.0.26100 and measured 100 waits per phase. Baseline P50/P95:
18.472/20.124 ms; while holding timeBeginPeriod(1): 4.749/5.569 ms; after its
matching timeEndPeriod(1): 18.729/20.152 ms. Both calls returned zero and a
finally block released the request. No persistent setting was changed. This
supports testing a scoped request in the receiver, but is still not Quinn or
presentation acceptance. Native presenter is a separate process and would
need its own scoped policy if that path is changed.
