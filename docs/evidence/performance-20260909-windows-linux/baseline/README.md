# Windows → Linux 6K 基线：阶段二

2026-09-09。用户指定的40%额度切换点已到，Linux→Windows优化组合已 [应用](../../performance-20260908/production-deployment/README.md)，现在开始优化反向链路，目标6144×3456、30FPS、延迟60ms。

## 已执行

从当前Windows反向源码构建硬件编码探针及wire/geometry测试。两项测试退出0；实际HEVC探针在6144×3456、编码器名义60Hz配置下提交并输出60帧，退出0，整个进程耗时6486ms（包含设备／编码器初始化及销毁）。**这是容量与编码路径检查，没有按真实帧率持续运行，不能换算为实际显示FPS或端到端延迟。** 源码、构建日志、原始输出及探针哈希保存在本目录。

探针二进制SHA256前缀162202e5，合成HEVC文件1754a141。当前安装的Windows反向程序仍为6ec79a73，尚未替换；Linux反向程序身份见method/installed-linux.json。源程序仍使用既有的成对QUIC反向通道。

Linux GPU解码探针原来只接H.264；已增加HEVC参数和逐帧预期尺寸检查，用于把同一份6K数据经过实际GpuDecoder解码和CUDA→GLES纹理导入。旧的H.264命令行保持兼容。Release构建成功，wire／geometry两项测试通过；同一HEVC样本实际解析60个access unit、GPU解码并上传60帧，尺寸均为6144×3456，GL错误0，设备为NVIDIA RTX PRO 6000 Blackwell。探针同时修复了末尾access unit尚未flush便退出的问题；修复前为59帧，修复后同一样本为60帧。此结果仅确认双端GPU编解码与CUDA→GLES路径可用，不代表持续吞吐或端到端延迟。

## 当前源码显示的测量重点

Windows主循环目前写死60Hz，最多允许4个待编码结果；WGC捕获纹理另复制到源纹理，再复制到atlas。每帧创建NV12编码输入纹理，另从GPU同步读回完整alpha平面，做CPU比较和必要压缩。6K单通道alpha约21.2MB/帧，这些操作应分段测量后再决定优化。

Linux接收队列上限为2，GPU解码后通过CUDA互操作复制到GL纹理，再逐代理提交Wayland表面。现有源Frame.pts在编码提交前生成，不能直接当作最初捕获时间；完整测量还需要对应捕获时间、编码输出、QUIC收发、GPU解码及桌面实际观察的帧身份。

尚未建立6K完整链路吞吐与延迟基线，没有把编码探针或仅GPU解码成功当作6K30／60ms验收。下一步先完成双端GPU路径检查，再加入具有帧标记和时间记录的被动6K窗口测量，保留真实输入的用户操作边界。
