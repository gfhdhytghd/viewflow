# Windows → Linux：6K30／60ms优化结果与额度收尾

2026-09-09，额度剩余40%时，Linux→Windows已测最优组合和帧率优先／延迟优先两个选项已经[应用](../performance-20260908/production-deployment/README.md)。随后进入本阶段。最后一次额度读取从先前的27%降至7%，已停止新增实验并按额度条件收尾。完整6144×3456、30FPS已达到，60ms尚未稳定达到。后续段落保留各阶段历史结论，以本段和最终收尾记录为准。

当前已安装的Windows反向程序为 **C914CC47…**，Intel HEVC 自动使用双任务 VPL。规范版四轮完整链路中，帧率优先为 **54.17–54.87FPS、P95 63.63–73.62ms**；延迟优先为 **40.51–41.92FPS、P95 77.60–77.90ms**。时延为绘制前至 Linux 桌面观察的估计上界，不含物理扫描。两个方向各自提供两个选项；主会话保持未启动，下次开启使用新版。[部署与回退记录](depth-deployment/README.md)。

[双端GPU基线](baseline/README.md)确认6K HEVC硬件编码、Linux GPU解码和CUDA→GLES导入可用。解码探针新增HEVC与尺寸检查，并修复文件末尾access unit冲刷，60帧样本完整通过。

## 完整传输测量更新

[6K完整传输对照](transport/README.md)已经覆盖 WGC、硬件HEVC和精确alpha、配对QUIC、Linux硬件解码与Wayland桌面观察。四轮同条件A/B/B/A测试中，编码速度设置0测得29.5–30.4个不同画面/秒，设置50测得25.5–27.5。设置0的延迟中位数约85–87ms，P95约102–104ms；其中一轮有619ms异常，原始结果保留。设置50的中位数81–96ms有明显波动，不能据此认定稳定的延迟收益。

源端独立输出已达到30.370个不同画面/秒，但不能替代完整链路结果。90个共同标记帧、每帧全部6K RGB像素的[画质对照](quality/README.md)显示该合成网格误差基本相同；尚不代表自然图像或细小文字画质相同。

所有延迟仍从源应用绘制前开始：源端Desktop Duplication观察会干扰性能，而DXGI呈现统计在该虚拟显示器上大部分返回零时间，随后一直重复同一个旧值，无法可靠分离源应用排队。当前没有物理屏幕扫描测量，完整6K30/60ms目标仍未达成。优化候选尚未覆盖已安装的Windows反向程序。下一步检查捕获到编码器之间的整帧拷贝，继续以实际完整链路对照决定保留方案。

## 整帧拷贝、透明度与调度复测

先前31轮完整链路的原始数据与[24轮候选对照表](transport/README.md#additional-copy-alpha-and-scheduling-comparisons)均已归档。自有源纹理直接提交与R8透明度摘要组合，两次开启测得31.24–31.53FPS，延迟估计中位78–83ms、P95为95–100ms，均优于这组对应关闭测试；仍未达到60ms。

在加入生命周期修复的相同程序上，跳过未变化画面使不同画面帧率从30.97–31.27提高到32.80–33.21FPS；四轮延迟区间重叠，尚不能确认稳定收益或代价。四种源流在相同90个画面标记上逐RGB像素比较，合成图案PSNR均约41.871dB；自然图像和文字质量还未据此验证。

静止窗口缩放后停止更新、窗口关闭后短暂发布错误元数据两个问题已修复。单窗口、多窗口、标题、位置、缩放、隐藏和关闭的21帧记录均通过Linux GPU解码、上传和逐像素透明度验证；这是离线生命周期检查，未替代实际Wayland窗口验收。当时31文件Windows构建及四项测试通过；下方记录了后续39文件规范构建及实际安装。

完整6K30/60ms目标仍未完成；当前规范版本及两个性能选项已安装，后续继续优化时延。源程序绘制前时间与最终桌面观察之间的时延估计，不等于物理屏幕扫描时延。


## 规范集成、调度复测与安装

完整链路现有43轮有效测量，新增队列、进程调度和规范构建的12轮[对照](transport/README.md#queue-bounds-process-priority-and-installed-canonical-build)。单帧／四帧上限下提交前队列均为空，未证明这项限制带来收益；进程Normal优先级的重复分布也交叉，因此不提高默认进程优先级。

最终39文件规范构建通过六项Windows测试，窗口生命周期与运行中三次模式切换通过GPU验证。复制期间尺寸变化会重做当前帧，避免发送被清空的透明窗口。程序已安装到原配置路径，完整SHA256为E1543F0754BAE0741955EF5FBD178262ED10AFE05E3845060E28AAC4121B93D0；已安装控制器的真实模式往返通过。源配置、原输入服务及显示矩形保持，主会话将在下次开启时使用新版。

本阶段仍未达到60ms。继续优化时保留已部署版本，并遵守额度剩余10%之前停止实验、应用已测最佳版本与两个选项的要求。

## Intel VPL 编码路径与当前部署

新增八轮完整链路测量，总计 51 轮有效记录。同一候选程序的 MFT/VPL 交叉对照中，旧编码器约 32.1–32.7FPS、中位 83.4–88.8ms，VPL 约 40.6–42.1FPS、中位 68.8–69.9ms。规范版复测保留了呈现时序造成的波动，没有把候选最佳中位数当作固定时延保证。[完整对照](transport/README.md#direct-vpl-and-canonical-automatic-selection)。

自有 NV12 纹理通过外部分配接口提交到 VPL，省去应用层额外复制；这不等于驱动内部没有复制。两列 HEVC 分块由运行库实际读回确认。内部纹理输出视图、共享导入和直接 RGB 输入的不支持结果，以及 13 个独立探针记录均保留。

957 帧 MFT 与 1181 帧 VPL 源流全部通过 GPU 解码和透明度检查。90 个共同画面的全部 6K RGB 像素比较得到两者 PSNR 均约 41.8995dB；这仅覆盖该合成图案。规范版通过六项 Windows 测试及 20 帧生命周期检查后已经安装，保留旧程序备份及两个性能选项。**60ms 目标仍未达到**，继续优化并遵守额度剩余 10% 前收尾的要求。

## WGC 采集间隔对照

新增八轮有效完整链路记录，总计 59 轮。实际默认采集间隔读回为 16 ms；取消默认间隔没有稳定收益，32 ms 间隔的帧率只有 29.61–29.79，第二轮 P95 达到 104.10ms。因此两项实验均未部署，已安装 VPL 最优版本保持。继续检查 Linux 接收与呈现耗时。[原始对照与失败构建](wgc-interval-v2/README.md)。

## Linux 接收与呈现分段计时

独立测量中，接收后等待中位 0.024ms、解码 4.60ms、纹理上传 0.071ms、绘制提交 0.382ms，普通几何查询中位 0.218ms。未发现这些环节存在持续积压；这组 CPU 计时不代表物理呈现完成。新增一轮有效完整链路结果为 41.10FPS、中位 69.71ms、P95 86.65ms；另有一轮日志交错已明确拒绝端到端分析。[分段数据与原始记录](linux-profile-v2/README.md)。

## VPL 两帧并行与缓存帧输出

新增八轮有效完整链路对照，总计 68 轮；同一程序分别验证一帧和两帧并行。第一版发现 MORE_DATA 缓存会影响静止输出、缩放和单帧模式，未部署。修正版显式请求缓存帧输出，21 帧生命周期和三次运行中模式切换均通过。完整链路结果、最大时延与实际深度读回见 [候选对照](vpl-depth-v2/README.md)。

## 异常长尾与 GPU 命令提交对照

新增八轮有效完整链路记录，总计 76 轮。两帧并行出现半秒以上长尾，5 ms 空闲合并并未消除。进一步增加 WGC 回调和 API 调用计时，并对照是否在自有纹理复制后立即提交 GPU 命令。所有最大值和异常间断均保留；尚未据此覆盖已部署版本。[诊断与对照](vpl-depth-v4/README.md)。

## 实际合成器与嵌套桌面对照

相同已安装源程序和相同 Linux 接收器的四轮交叉对照中，实际合成器独立虚拟屏 P95 为 81.70–85.47ms，嵌套桌面为 80.97–95.08ms，区间重叠，未发现嵌套层造成固定额外一帧的证据。首轮顶部标记失败已作废；复测将标记移到窗口内部，两侧使用相同标记和观察位置，并保留图片及桌面叠层记录。[测量方法与结果](root-headless/README.md)。

## 有序缓存输出与双任务规范版

VPL 在排出缓存帧前先完成已有编码任务，排出期间暂停新提交，确认全部输出后恢复；短暂捕获空档先合并 20ms，单帧模式和尺寸变化立即请求缓存输出。组合修复的一帧／两帧四轮对照均保留，未单独归因两个调整。规范版再做四轮模式验证，总计 89 轮有效完整链路测量。22 帧候选和 21 帧规范版生命周期、三次模式切换、完整 GPU alpha 与 90 个共同画面全 6K 像素质量对照通过。[实现与测量](root-depth/README.md)、[候选结果](vpl-depth-v5/README.md)、[画质](depth-quality/README.md)。

## 编码输入纹理绑定对照

四轮同程序独立探针比较普通 NV12 渲染目标与额外编码输入绑定。均成功编码／GPU 解码 120 帧，四个码流逐字节一致；耗时中位均约 18ms，没有稳定收益，未部署。[原始记录](vpl-probe-v9/README.md)。

## 双任务编码与采集间隔组合

双任务后重新交叉验证：默认 16ms 采集间隔为 53.46–54.46FPS、P95 63.95–66.77ms；零间隔为 58.47–59.76FPS、P95 68.14–74.09ms。帧率提高但延迟升高，尚未部署；继续验证公开模式组合。累计 93 轮有效完整链路。[记录](depth-interval/README.md)。

## 两个在途画面的外层上限

将外层在途上限从四降到二后，两轮只有 48.46–48.51FPS，P95 升到 81.85–85.09ms；未采用，现有两种模式上限保持四／一。累计 97 轮有效完整链路。[隔离对照](depth-limit/README.md)。

## AV1 与专用 CUVID 解码探针

AV1 在实际硬件上可编码完整 6K，运行库将分块改为两列两行，但该配置编码路径中位约 23ms，慢于 HEVC 约 18ms，未采用；全部文件已验证 GPU 解码。[编码器对照](vpl-probe-v10/README.md)。Linux 专用 CUVID 在 120 个输入后仅及时输出 119 帧，单个静止首帧也被缓存，因此拒绝直接替换现有解码器。[单帧与末帧检查](cuvid-probe/README.md)。

## NV12 直接计算写入

[资源接口检查](nv12-uav-probe/README.md)确认完整 6K NV12 的 Y／UV 两平面可由计算着色器写入。随后四轮同程序对照中，计算转换的 GPU 区间中位约 12.7ms，视频处理器约 3.9ms；计算路径更慢，且两种转换码流不同，未采用。全部 480 帧已经 GPU 解码与 GLES 上传验证。[性能与范围](vpl-probe-v11/README.md)。

## 推迟不必要的编码器排空

四轮新对照把累计有效完整链路增加到 101 轮。二帧模式 P95 降到 70.47–72.78 ms，仍未达到 60 ms；21 帧生命周期和模式切换通过，尚未部署。[源代码与验证](depth-limit-v2/README.md)。

## 同一画面的完整阶段配对

新增五轮带标记的完整链路诊断，累计 106 轮有效测试。绘制到 WGC 复制约 24.4–24.6 ms，编码约 21 ms；零采集间隔未消除固定采集等待，最好单轮 P95 为 61.29 ms，仍未达标。[逐帧证据](marker-profile/README.md)。

## 码率控制与视频处理附加设置

固定 QP、普通 P 帧和关闭视频处理器自动处理均未显示有效加速，未采用。固定 QP 初始缓冲容量不足的问题在隔离测试器中修正，失败原始记录保留；后续八轮编码输出全部解码通过。自动处理四轮输出完全相同。[码率／帧类型对照](vpl-probe-v13/README.md)、[自动处理对照](vpl-probe-v14/README.md)。

## 排空与采集间隔组合

累计 112 轮有效完整链路。四帧上限加零采集间隔的两轮达到 57.11／59.06 FPS、P95 58.42／58.96 ms，符合当前测试判据；第一轮仍有 274.21 ms 最大值。两帧模式仍波动，正在补充较长观测与正式接口版本验证。[组合试验](depth-combined/README.md)。

## 较长观测未能复现低于 60 ms

累计 114 轮有效完整链路。100 秒观测中，正式接口候选四帧／两帧模式 P95 为 86.78／77.76 ms，均未稳定达标，未部署。源端额外排队和编码尾部等待已被逐帧记录，正在检查调度等待。[长测与生命周期](mode-combined/README.md)。

## 最终收尾

共 115 轮有效完整链路测量，另保留被拒绝的启动和探针失败。最后的等待诊断未显示 15.6 ms 睡眠量化；窗口扫描和 alpha 查询偶发较慢，留作后续证据，没有继续修改调度策略。6K30 已满足，60 ms 仍未稳定实现。按额度停止条件结束本轮，采用已安装的 C914，保留帧率优先／延迟优先；最终本机与 Windows 的程序、配置、服务和显示状态复核见 [收尾状态](depth-deployment/method/after-followup-probes.json)。
