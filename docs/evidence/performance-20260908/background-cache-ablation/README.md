# 4K 背景缓存开销分解

**因用户观察到测试画面只有半透明且鼠标受干扰，完成前三轮后暂停。完整反序对照未完成，本目录不用于宣称模糊已验证或四模式性能因果结论。后续已单独完成测试窗口鼠标穿透修复与可见背景条纹验证，见相邻 passive-blur-validation 目录；未恢复本组全屏实验。**

本实验以实际 HDMI 3840×2400、约 60 Hz 为输出，源内容、捕获和 atlas 尺寸分别为 3840×2400、3848×2408、3968×2432。观察器要求唯一活动的 3840×2400 输出，窗口按 1:1 放置；没有将 6K 次屏作为替代。

## 四种模式

| 模式 | 后台采样窗与 WGC | 后台比较、模糊及发布 | 前台背景 |
|---|---|---|---|
| off（0） | 无 | 无 | 原有实时背景 |
| capture（3） | 30 Hz 请求刷新并获取帧 | 不执行，帧直接关闭 | 原有实时背景 |
| process（4） | 同上 | 完整执行并消费、回收缓存槽 | 原有实时背景 |
| cache（2） | 同上 | 完整执行 | 使用缓存背景 |

原计划运行顺序 off / capture / process / cache / cache / process / capture / off；实际仅前三组完成。所有模式使用同一份原生程序、同一启动器和相同源端、Rust receiver、动画及观察器。每轮源持续 55 秒，桌面观察 30 秒，检查动画存活及完整覆盖。模式通过独立启动器的进程环境设置，不改变产品默认配置。

capture 模式保留同样的初始化与采样宿主，在获取 WGC 帧后直接关闭，未执行逐帧比较、模糊或发布；初始化资源不等于没有任何 GPU 工作。process 模式继续运行已有 GPU 工作和槽回收，但从进程启动起始终不绑定缓存，也不在每次更新时重新设置前台画刷。故 capture 对 off 的差异包含后台框架、辅助采样窗和捕获，不能单独命名为 WGC API 成本；process 对 capture 包含比较、模糊、发布及回收，不能单独命名为比较着色器成本；cache 对 process 同时包含绑定缓存与替换原实时模糊的效果。

## 实现与功能核对

候选从[背景变化检测](../background-change-detection/README.md)的完整源树复制，仅新增两个诊断开关与诊断输出。产品源码和默认运行程序未替换。[108 文件源清单](method/source-sha256.json)与[远端回读](method/remote-source-hashes.json)一致。MSVC Release 构建成功；初版之后做了一次小修正，使 observe 模式完全跳过画刷重置，所有性能运行都使用修正后的同一个二进制。

同次构建的常规缓存测试通过：静止背景复用、后方本地窗口颜色变化、移动、缩放、透明洞、恢复以及屏幕边界；没有输入注入，测试窗口未获得前台焦点。1132×1132 条纹区域在移动回相同位置后，缓存逐字节相同，原始背景因 0/0.01 像素刷新偏移最多差一个码值。[运行记录](method/native-background-result.log)、[像素比较](method/worker-pixel-comparison.json)。这不代表两种诊断模式完成了独立的全图 oracle；它们的执行路径将由实际运行计数核对。

## 测量限制

原生提交次数不是屏幕刷新次数。Desktop Duplication 可漏观中间帧；marker 对应的 LastPresentTime 不保证是首次呈现，更不是光子时刻。延迟为包含时钟不确定度的所见桌面上界。所有桌面不同帧计数统一除以完整 30 秒，不用短区间放大速率；阶段中位数不能相加或作为逐帧相减的替代。性能目标仍是实际 4K60、两帧内显示，不能用诊断模式或局部阶段改善替代该目标。
