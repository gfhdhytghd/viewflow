# Hyper-V 与 DDC 修复后的 Intel 遥测优先级复测

当前条件下，普通优先级再次减少了慢回执，并使原生提交率达到约 59.8–59.9 次/秒；但桌面观测率和完整延迟没有稳定改善。**测试后已恢复原 High/TimeCritical 设置，未添加自动调节第三方进程的产品逻辑。4K60、两帧内显示仍未证明。**

本轮保留已应用的 Hyper-V 计时补丁与后台 DDC/CI 亮度读取修复；同一 Linux 源、延迟优先捕获、Windows receiver/native/observer，只改变 Intel 遥测服务的优先级。源 55 秒、DD 观察完整 30 秒，实际 HDMI 3840×2400@60、源 3840×2400、atlas 3968×2432；H.264、完整 sigma=12 host blur、背景缓存／直接绘制／GPU 查询关闭。

## 已核实的控制

服务 `ESRV_SVC_QUEENCREEK` 运行于 PID 8628。原进程 High；线程 9644、11788 为 TimeCritical/base 15，其中 11788 的累计 CPU 时间明显更高。每次控制同时核对服务 PID、进程创建时间及两个线程创建时间；普通组将进程和这两个线程设为 Normal/base 8，恢复组回到 High/TimeCritical。每轮前后读回优先级和服务 Running/Auto；没有停止或重启服务，没有更改网络适配器、注册表、驱动、显示几何或输入路由。

独立十分钟 SYSTEM 恢复任务在第一次修改前注册；正常结束路径恢复原状态并删除恢复任务。控制器另行保存全过程，`priority-control.json` 的最终记录确认同一进程和线程恢复。读回发生于每轮前后，不是连续调度跟踪，也不声称服务在所有时刻都没有自行改变线程属性。

所有 acquired 标记有效，源/接收时钟和唯一帧身份对应通过分析检查，长尾未裁掉。Linux/Windows 窗口均为被动，未注入输入或焦点；临时输出与嵌套合成器清理，原几何和插件列表保持一致，Windows VDD 配置不变，私有任务、进程和 49073 端口清空。已应用的后台亮度修复脚本哈希在每轮记录中相同。

`method/verify-archive.py` 从压缩日志重算四轮，并验证运行二进制、捕获入口、线程创建时间／优先级前后读回、恢复状态、清理和归档哈希。此候选是特定机器的调度对照，尚未决定在额度收敛时是否采用机器级配置；不会仅凭这里的局部提交率宣布 4K60 达标。
