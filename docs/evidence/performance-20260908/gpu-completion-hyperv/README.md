# Hyper-V 计时补丁后的 GPU 完成查询对照

四轮保持延迟优先捕获，只改变 `VIEWFLOW_ATLAS_GPU_QUERIES=0/1/1/0`。未测得稳定的端到端提升；查询是诊断，不作为产品优化部署。4K60、两帧内显示仍未证明。

原生接收、Linux 源、fixture、捕获插件均沿用[两档模式接线复测](../performance-mode-integration/README.md)的相同二进制。仅新建私有启动器选择查询开关；启动器源码、MSVC 构建与哈希在 `method/`。实际 HDMI 输出 3840×2400@60，fixture 3840×2400，捕获 3848×2408，atlas 3968×2432；H.264、完整 sigma=12 host blur、背景缓存关闭、直接绘制关闭。每轮源 55 秒，Desktop Duplication 观察完整 30 秒。正常配对、输入和连接策略均未改动。

开启查询的两轮，共 1748 / 1727 个桌面标记全部关联唯一捕获和 GPU 完成事件，无缺失或多义关联。提交 surface copy 后仍未完成的最后一次查询时刻，下界中位分别为 15.331 / 15.373 ms；最早观察到完成的查询时刻，上界中位为 30.670 / 16.884 ms。这里的下、上界分别是同一总体各自的分布，不表示同一典型帧的精确耗时，也不能将 GPU 队列事件解读为 DWM 已完成。

现有查询只在 `Advance()` 中执行，等待下一条 pipe / decode 事件时不轮询。因此完成区间可宽达一帧，有些查询上界晚于该标记的桌面时间，导致“完成上界→桌面”的下界为负。这表示轮询上界过晚，不能解释为负的物理延迟，也不能据此把剩余时间全算作 DWM。下一步是隔离测试更细的查询间隔。

所有取得的标记均有效，时间戳和 marker ID 递增，完整长尾保留。DD LastPresentTime 是包含该内容的一次桌面更新时间，不保证首次显示，不是光子；原生提交率与不同标记观测率均不是已验证的物理 FPS。

四轮均为被动窗口：Linux 空输入区域，Windows transparent/no-activate，中心与四角只读命中检查通过，没有输入或焦点注入。私有嵌套合成器和临时输出已移除，原始输出几何、插件列表、VDD 配置、ESRV 进程和优先级保持一致，测试进程、任务和 49073 端口清空。`method/verify-archive.py` 离线重算原始日志、逐帧关联、二进制身份与归档哈希。

本组运行期间还编译了下一组细轮询诊断的 Windows 原生程序，编译负载未逐帧隔离。因此四轮端到端差异不能用于估计 GPU 查询开关自身的因果影响；这里的有效用途是完成事件与帧身份的关联、轮询上下界及方法限制。没有据此部署性能候选。
