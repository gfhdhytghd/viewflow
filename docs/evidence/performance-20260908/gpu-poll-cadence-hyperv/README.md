# GPU 完成查询的细轮询对照

四轮保持相同查询开启状态及延迟优先捕获，只比较原来随帧到达查询与空闲时 1 ms 查询。细轮询缩小了完成时间的范围，但没有稳定降低完整延迟，诊断保留在隔离原型中，不进入产品默认配置。4K60、两帧内显示仍未证明。

候选只改 `main.cpp`：`VIEWFLOW_ATLAS_GPU_POLL=1` 时，若存在待完成 GPU 查询，将原生 pipe/decode 消息等待上限从无限改为 1 ms，并在主消息循环非阻塞轮询查询；没有等待 GPU 工作、强制刷新、重新设置提交顺序或改变接收策略。无待完成查询或开关关闭时沿用无限事件等待。`DONOTFLUSH` 不变，所有查询只描述应用 D3D 队列，不是 DWM 完成通知。111 个远端源文件与保存树一致，MSVC Release 构建通过。

上下界的中位数分别描述同一总体，不是同一具体帧，不能相加重建端到端中位数。两轮细轮询确实缩小区间，已观察完成后的队列／合成／显示等待仍然明显；不能只凭此分段命名为 DWM CPU 用时。DD LastPresentTime 是包含该标记的一次桌面更新时间，未保证首次显示，也不是光子。原生提交率和不同标记观测率不能充当实际物理 FPS。

测试保持 HDMI 3840×2400@60、源 3840×2400、atlas 3968×2432、H.264、sigma=12 完整背景模糊、背景缓存与直接绘制关闭。源 55 秒、桌面采样完整 30 秒，全部 acquired 标记有效，长尾保留。相同源端、fixture、观察器，Windows 原生四轮同一哈希，仅启动器中的细轮询环境变量不同。所有 Linux/Windows 测试窗口均被动，未注入输入或焦点；私有嵌套合成器和输出移除，原显示器几何与插件保持一致，Windows 任务、进程和端口清空，VDD 与 ESRV 状态保留。`method/verify-archive.py` 可离线重算四轮原始日志与身份、检查源和归档哈希。

检查这些数据时另外发现 Linux 编码每十秒出现 230–250 ms 停顿，与桌面状态栏 DDC/CI 亮度读取同步。这个线索正在[单独对照](../periodic-ddc-stall/README.md)，不据此修改或解释掉本轮数据。
