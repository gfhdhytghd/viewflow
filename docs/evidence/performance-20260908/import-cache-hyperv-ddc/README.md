# DMA-BUF 导入缓存在 Hyper-V 与 DDC 修复后的复测

**缓存重复节省约 1 ms 编码时间；开启两轮的桌面观测更新率较高，但完整延迟没有稳定下降，暂不替换生产默认。** 四轮都未证明 4K60、两帧内首次显示。开启 B1 的捕获→桌面唯一配对样本最大值约 31 ms，但完整绘制前→桌面仍有 44 ms 样本；B2 保留约 158 ms 长尾，不能截取单轮或单阶段宣称达标。

## 方法与范围

从当前工作树复制 228 个 Rust、协议及 NVENC 源文件，唯一源码差异为既有 `gpu_dmabuf_encoder.cu` 缓存原型。当前 Rust 性能模式实现保留。四轮使用同一个隔离 sender，环境变量 `VIEWFLOW_GPU_IMPORT_CACHE=0/1/1/0` 控制关／开／开／关；GPU 细分日志采用相同采样设置。每帧仍保留 native fence、CUDA map/unmap 和读取完成同步；缓存保存注册与存储引用，不缓存帧内容。

Windows receiver、原生呈现器及观察器沿用 Hyper-V 修复后的已核对二进制，保持完整 sigma=12 host blur、普通输出路径、背景缓存关闭、GPU 查询关闭。Intel 遥测进程优先级保持原设置；本批次没有调整该进程或线程。每轮核对已应用的亮度状态脚本哈希，避免恢复每十秒 DDC 查询的旧脚本。

Linux 使用隔离嵌套 Hyprland、3840×2400 GPU fixture、scale 2，atlas 3968×2432；Windows 观察器要求唯一实际 3840×2400 输出。每轮 source 55 秒、DD 观察 30 秒，采用延迟优先捕获、60 Hz。构建与 GPU 正确性测试全部在四轮测量开始之前结束。测试窗口使用空输入区域／鼠标穿透及不激活属性，没有注入输入或调用焦点切换。

DD LastPresentTime 表示含相应 marker 的一次桌面更新时间，可能不是第一次显示；报告保留时钟不确定度。原生提交速率、30 秒内观察到的不同 marker 数及物理刷新率是不同指标，不能相互替代。完整绘制前→桌面上界包含捕获前等待；采集→桌面单独报告，所有有效长尾保留。

## 正确性及复算

缓存开启时 CTest 7 项通过；当前候选的额外 3840×2400 GPU 集成测试通过完整 alpha、颜色／GOP、atlas 切换、native fence 及测试注入过期后的恢复。缓存源码与[原型的持久存储复用 oracle](../dmabuf-import-cache/README.md)逐字节相同；那份 64 帧 oracle 检查了同一数字 FD 的不同存储、命中内容更新、容量淘汰、完整 alpha 和软件解码颜色。旧 oracle 是该缓存实现的既有证据，本轮另记录当前集成测试，没有声称重新执行旧 oracle。

`source-tree` 保存候选完整源快照，`method/root-source-sha256.json` 与 `candidate-source-sha256.json` 标明唯一源码差异。第一次复用隔离 Cargo 依赖缓存时，旧 CMake cache 的源目录不匹配；保留失败日志，删除该隔离构建目录后重建成功，生产构建目录未受影响。

测量脚本内包含当时的私有路径及主机地址，重跑前必须重新核对运行身份；不会归档配对私钥或配置明文。`method/verify-archive.py` 只离线解压与复算四轮原始日志，检查时间线、导入统计、二进制、被动窗口检查、嵌套捕获及清理快照，再验证 SHA256。运行 `python3 method/verify-archive.py` 不创建测试窗口。

最终清理快照确认私有测量进程、任务及 49073 端口占用均为 0，原 VDD 配置哈希一致；自有输出与嵌套 compositor 已退出，原监视器几何及根捕获插件保持不变。Intel 遥测仍为同一 PID 的 High，亮度脚本保留已应用的按需读取版本。本轮未替换生产 sender 或捕获插件。
