# 移除后台 DDC/CI 亮度读取：周期性编码停顿消失

四轮原脚本／按需读取／按需读取／恢复原脚本的对照确认：**后台亮度轮询会触发每十秒一次的 225–246 ms 编码停顿。移除重复读取的两轮均无这类停顿，恢复后重新出现。按需读取版本已应用到当前桌面的状态脚本。** 原生提交率从 58.50 / 58.14 升到 59.42 / 59.53 次/秒；完整显示延迟仍不稳定，4K60、两帧内显示未证明。

## 实际改动

`~/.config/HyprV/quickshell/scripts/control-panel-status.sh` 原来在每次状态轮询中执行亮度脚本 `--get-level`。面板关闭时每十秒轮询，DDC 后端每次调用 `ddcutil getvcp 10`。本改动只删除这个重复的亮度段，不输出 `brightness=` 字段，因此状态解析器保留已有亮度值。Wi-Fi、勿扰、录屏、电源、睡眠、风扇等状态输出保持原有行为。

面板打开时已有 `refreshBrightnessStatus()` 独立读取真实值；滑块、亮度快捷键与调整后 debounce 查询也保留。实际亮度读写脚本、硬件亮度值、快捷键、焦点及输入路由均未修改。用户从显示器自身菜单修改亮度，会在打开控制面板或原有主动刷新时读回；后台不再每十秒读取一次显示器。没有以周期性伪值替代真实读回。

生效路径及原脚本备份记录在 [application.json](method/application.json)。脚本每次由状态栏重新调用，无需重启 Quickshell。安装后的字节摘要与测试候选一致，`bash -n` 通过；直接只读调用验证其余状态字段仍完整。没有代用户执行亮度调整或打开面板。应用后再观察 23 秒，捕获到状态脚本进程，未见 DDC 查询进程；记录在 `method/applied-processes.json`。

## 因果对照与时间关联

先前只读进程观测发现 `ddcutil` 执行区间与源端编码停顿重合。四轮只替换状态脚本原版／候选版；源端、fixture、捕获插件、Windows 原生接收器、观察器等二进制均保持一致。两轮候选累计超过 6,400 个 frame≥30 的编码记录没有一次超过 20 ms；原版分别有 5 / 6 次超过 150 ms 的周期性停顿。恢复轮另外两次 20.2 / 25.4 ms 非周期性停顿仍保留。20 / 150 ms 只用于描述日志分布，不是产品丢帧或连接边界。

进程观测覆盖的七次长停顿，每次都与一个 `ddcutil` 生命周期区间重合；候选的两个阶段内没有新的 DDC 查询。观测器 20 ms 扫描进程子树，有采样误差；不把 first-seen/last-seen 当作精确进程起止，也不把时间相关性单独当作因果结论。因果判断来自四轮恢复对照。另一个旧诊断的细分记录显示长等待分布在 EGL/CUDA 导入调用中；本次并未追踪驱动内部锁，不能指定某一条驱动函数为根因。

## 测量范围与复算

实际 Windows HDMI 输出 3840×2400@60，fixture 3840×2400，捕获 3848×2408，atlas 3968×2432；相同延迟优先捕获、H.264、完整 sigma=12 host blur，背景缓存和直接绘制关闭、GPU 查询关闭。源各运行 55 秒，桌面观察完整 30 秒。所有 acquired 标记有效；第一候选有 8 次重复标记，完整 acquired=1707、不同标记=1699，两种计数不混用。

DD LastPresentTime 是含该标记的一次桌面更新时间，未保证首次显示，也不是光子。源与接收时钟按已有 QUIC 四时间戳校准并保留不确定度，按真实标记身份关联。原生提交率、桌面观测率均不是已验证的物理 FPS。

Linux/Windows 窗口均被动，无输入或焦点注入。四轮结束先恢复原脚本，再根据结果应用候选；两个动作分别在嵌套控制器状态与 application.json 中保存。测试输出和嵌套合成器移除，原有几何／插件、Windows VDD／ESRV 状态保持一致；私有任务、进程和 49073 端口清空。

`method/verify-archive.py` 离线重算四轮原始日志、二进制和状态脚本身份、捕获模式与归档哈希；`method/analyze-stalls.py` 重算进程时间关联。只读系统 perf trace 因本地 sudo 需要密码未能启用，保留错误日志，后续使用普通权限的 `/proc` 子进程观测，没有更改系统权限。
